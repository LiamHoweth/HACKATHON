# Judge Q&A

These answers are grounded in the evidence as of 11:30 CT. **Reconcile them with [TEST_RESULTS.md](TEST_RESULTS.md) and [PRESENTATION_LOG.md](PRESENTATION_LOG.md) just before judging.** Replace "not measured" or "not verified" only with recorded results.

| Question | Answer |
| --- | --- |
| **How reliable is the blink detection?** | **Not measured yet.** *(After the gate, give the counts from TEST_RESULTS: number of intentional trials, missed gestures, false selections, false confirmations, gesture duration median/range, plus the room and tester.)* It's a small team test, not a reliability study, and it says nothing about people with ALS. Ordinary blinks are filtered by a calibrated minimum closure duration. Speaking always needs a second, separate blink. |
| **Is the camera recording me?** | No recording is designed in. Frames go to a face-landmark model running in the browser, loaded from our own server. The model gives eye-closure scores and a face count, and the app keeps only calibration numbers such as thresholds and durations. *(Say "and we confirmed no frames are uploaded in the network log" only after SYS-13 is recorded.)* No face recognition, gaze tracking, or emotion detection. The camera stays off until you consent, and other input modes never ask for it. |
| **What if I blink normally?** | Short natural blinks are below the calibrated minimum closure and are ignored. Both eyes must close, so winks don't count. A selection takes a deliberate, longer closure. Reaching speech needs a second deliberate closure on Speak, on a review screen that starts on Cancel. Real false-selection counts: *not measured / from the gate*. |
| **What if someone else walks into the frame, or I look away?** | If the face is missing for more than half a second, any closure in progress is discarded. Coming back selects nothing by itself, and a new deliberate closure is needed. With two faces, nothing can be selected until one face is stable again. The detector looks for up to two faces for this reason. That's in code and synthetic tests. *(Say "verified on camera" only after ACCESS-14 and gate part D.)* Face count is not identity, though. We don't claim to know who is in front of the camera. |
| **Has this been done before?** | Yes. AI-assisted AAC and webcam- or eye-controlled AAC both exist. VisioALS, Bobbai, Speak4Me, Google's SpeakFaster, and Project Converse are research leads in our references. We haven't independently verified them. We are not claiming a first. |
| **What is your contribution?** | A specific working combination built today: blink selection over automatic scanning with individual calibration, semantic "None of these" scoped to one question, explicit intent guidance, conversation continuity, and consent-gated preferences, all through one guarded engine with exact review and separate confirmation. *(List only items verified in the presentation log.)* |
| **Why AI rather than predictive typing?** | The hypothesis is that choosing a whole message takes fewer blinks than spelling it. We **have not measured** that. My words, a scanning keyboard, is always available. |
| **What happens when the AI is wrong?** | Reject all three, guide the direction, ask for "same idea, shorter", or write your own. After two rejected batches the app offers "Write it myself". |
| **Could it accidentally speak?** | Speaking needs a selection, then a separate confirmation from a different input cycle (for blink, a new closure), on the current screen, at least 600 ms after review opens. Review starts on Cancel. Each utterance plays once. 82 unit/API tests pass. Browser checks with synthesized keys passed. **Not yet tested with real blinks.** Residual risk: someone can still deliberately confirm the wrong message, so review shows the exact text. |
| **What happens without internet?** | Blink detection and Quick phrases/My words don't need the AI. Offline behavior after a network drop, and whether the voice is local, are **not verified**. |
| **How does it learn?** | Only with session adaptation on, and only sentence length. After 3 different turns it may offer a suggestion. Nothing is saved without "Yes, remember this" and a separate confirmation. |
| **Does rejection teach it my opinions?** | No. A rejection means "not these, for this question". It is cleared afterward and never stored. |
| **Can someone with ALS use it?** | We don't know. Access needs vary, and blinking won't work for everyone. That's why calibration can fail openly and keyboard/switch/pointer remain. **No one with ALS or any AAC user has tested it.** |
| **What did you measure?** | *(From TEST_RESULTS only.)* As of 11:30: nothing. Live AI returned valid batches in ~4 s in single synthetic calls. That's an observation, not a latency study. |
| **Have AAC users tested this?** | **No.** Only the team. No study or partnership is arranged. |
| **How is privacy handled?** | Camera: in-browser processing (network check pending). Live AI: bounded context sent to OpenAI with `store: false`. We have not reviewed their retention terms. Audio goes to transcription only after consent and Record. Logs carry no content. Only approved preferences are stored, and only if you choose "Remember on this device". |
| **Did you use live AI in the demo?** | *(Say what the badge shows.)* Live OpenAI `gpt-6-astra` was verified today with synthetic inputs. The fixture mode is labeled. |
| **Is there a mobile app?** | An experimental SwiftUI client exists in the repo. It builds and passes simulator unit tests, but it has never been run end to end and is not part of the demo. |
| **How was AI used to build this?** | Claude Code implemented it under Liam's direction and review. See [AI_USAGE.md](AI_USAGE.md). |
| **What comes next?** | Planned, not arranged: co-design and evaluation with AAC users and specialists, a measured blink-vs-keyboard comparison, and broader access methods. |
